# 流程管理需求分析（初版）

> 2026-04-07 更新说明：本文现作为“高级流程管理能力”分析文档保留。当前产品优先级已调整为内置流程模板与模板配置中心，详见 `docs/2026-04-07-product-scope-and-built-in-workflow-plan.md`。

## 1. 文档目的

本文档用于明确审批系统中“流程管理”模块的建设目标、业务范围、核心需求、角色权限、业务规则与非功能要求，为后续概要设计、详细设计与开发实现提供依据。

本文档聚焦于：

- 流程定义管理
- 流程版本管理
- 流程发布与停用
- 流程节点元数据配置
- 流程与表单版本绑定
- 流程实例与版本追溯

本文档不覆盖完整拖拽式流程设计器、复杂脚本引擎、跨系统流程编排与运行中实例热迁移。
本文档默认面向技术管理员或高级配置场景，不作为普通业务用户的直接操作界面设计依据。

## 2. 背景与问题

当前系统已基于 Flowable 实现了审批流程执行能力，支持：

- 单人审批
- 会签
- 或签
- 串行审批
- 草稿、提交、认领、审批、委派、转办、回退、挂起、激活、撤销
- 审批日志与业务台账记录

现有流程能力主要依赖：

- 预置 BPMN 文件
- 运行时流程变量
- 服务层业务逻辑
- `biz_request`、`biz_request_task`、`biz_request_log` 等业务表

该实现已具备“流程执行”能力，但仍缺少“流程管理平台”应有的管理层能力，具体问题如下：

1. 流程定义不可见
   - 系统中有哪些流程、各流程用途是什么、当前使用哪个版本，缺少统一管理入口。

2. 流程版本不可控
   - 新旧流程定义之间缺乏清晰版本管理，无法明确某个业务申请使用的是哪个流程版本。

3. 发布过程不可管理
   - 流程变更更多依赖代码和部署动作，而不是系统内的“发布、停用、归档”行为。

4. 流程与表单关系不清晰
   - 虽已有表单版本锁定能力，但流程版本与表单版本的绑定关系尚未作为流程管理对象统一维护。

5. 节点业务规则缺乏元数据管理
   - 节点审批方式、审批人策略、AI 建议开关、退回能力等规则没有形成统一配置模型。

6. 实例追溯链不完整
   - 当前申请单与具体流程定义版本之间的关联需要补强，才能满足审计、运维和版本回溯需求。

因此，需要在现有 Flowable 执行能力之上，补充流程定义元数据和版本管理能力，使系统具备基础流程管理平台能力。

## 3. 建设目标

本模块建设目标如下：

1. 建立统一的流程定义主档
   - 管理员可查看、维护系统中的流程定义清单。

2. 建立流程版本管理机制
   - 每个流程定义支持多版本，明确当前启用版本与历史版本。

3. 建立系统内发布机制
   - 流程版本的启用、停用、归档应成为平台行为，而非单纯部署行为。

4. 建立节点级元数据配置能力
   - 在 BPMN 结构之外，管理节点审批方式、审批人策略、操作能力等业务规则。

5. 建立流程版本与表单版本绑定关系
   - 保证流程实例启动后所依赖的表单结构可追溯、可冻结。

6. 建立实例版本追溯能力
   - 任意业务申请单可反查其对应流程定义、流程版本、表单版本。

7. 保持与现有 Flowable 执行机制兼容
   - 流程运行仍由 Flowable 驱动，本模块负责管理层、版本层、元数据层。

## 4. 适用范围

本次流程管理需求适用于本审批系统内的流程配置与运行管理。

包含范围：

- 流程定义管理
- 流程版本管理
- 流程发布、停用、归档
- 流程与表单版本绑定
- 节点配置管理
- 流程实例版本追踪
- 发布审计记录

不包含范围：

- 在线自由拖拽 BPMN 建模器
- 自定义脚本表达式执行引擎
- 多租户流程隔离
- 跨系统编排与集成编排
- 流程运行中实例迁移到新版本
- 全量低代码平台能力

## 5. 相关角色

建议本模块涉及以下角色：

### 5.1 设计人员 `DESIGNER`

负责流程定义维护、版本草稿创建、节点配置、表单绑定配置。

可执行操作建议包括：

- 新建流程定义
- 创建新版本草稿
- 编辑草稿内容
- 查看流程版本
- 查看节点配置
- 复制历史版本生成新草稿

不建议直接拥有发布、停用、归档权限，除非系统单独授权。

### 5.2 管理员 `ADMIN`

负责流程版本发布、停用、启用、归档及全局审计查看。

可执行操作建议包括：

- 发布流程版本
- 停用流程版本
- 启用已停用版本
- 归档流程定义
- 查看发布日志
- 查看流程实例版本使用情况

### 5.3 普通用户 `EMPLOYEE`

负责发起业务流程、处理审批任务、查看个人相关申请和任务。

与流程管理模块的关系主要为：

- 使用当前启用的流程版本发起流程
- 在查看申请单时可看到流程名称与版本信息
- 无权修改流程定义和版本

## 6. 业务术语

- 流程定义：流程的业务主档，如“差旅申请流程”“报销审批流程”。
- 流程版本：某个流程定义的具体版本实体，包含 BPMN 内容、绑定表单、节点配置等。
- 当前版本：某流程定义下当前允许发起新实例的版本。
- BPMN：流程执行模型文件，由 Flowable 解析并执行。
- 节点配置：某个流程版本下，对具体节点的审批方式、审批人策略和操作能力的配置。
- 表单版本：动态表单的具体版本，与流程版本绑定后，实例启动时形成固定快照。
- 发布：将一个草稿版本校验通过后登记为系统可用版本，并部署到 Flowable。
- 停用：禁止某个已发布版本继续用于新实例发起。
- 退休：将历史版本转为仅保留审计用途的冻结版本。
- 实例追溯：从申请单回查其使用的流程定义、流程版本与表单版本。

## 7. 总体业务原则

本模块遵循以下原则：

1. 流程执行与流程管理分层
   - Flowable 负责执行引擎能力
   - 流程管理模块负责定义、版本、发布、绑定和追溯能力

2. 已发布版本不可直接覆盖修改
   - 若需变更，必须生成新版本草稿

3. 同一流程定义任一时刻仅允许一个当前可发起版本

4. 历史实例与其启动时所用流程版本永久绑定
   - 不因后续新版本发布而变化

5. 流程版本与表单版本绑定后，实例启动即形成固定快照

6. 版本状态变化不影响历史实例查询与审计

## 8. 功能需求

### 8.1 流程定义管理

系统应支持建立流程定义主档，用于描述系统中的流程清单。

应支持的能力：

- 新建流程定义
- 查看流程定义列表
- 查看流程定义详情
- 修改流程定义基础信息
- 启用/停用流程定义
- 归档流程定义

流程定义应至少包含以下信息：

- 流程唯一标识
- 流程名称
- 分类
- 描述
- 当前状态
- 当前版本
- 创建人与更新时间

业务要求：

- 流程唯一标识必须全局唯一
- 已产生实例的流程定义不得物理删除
- 停用后不允许继续发起新实例
- 已归档流程仅保留查询和审计能力

### 8.2 流程版本管理

系统应支持对同一流程定义维护多个版本。

应支持的能力：

- 创建新版本草稿
- 查看版本列表
- 查看版本详情
- 复制历史版本生成新草稿
- 维护版本说明
- 查看版本绑定的表单版本与节点配置

每个流程版本应至少能够管理：

- 版本号
- 状态
- BPMN 内容
- Flowable 部署关联信息
- 绑定的表单版本
- 版本变更说明
- 发布时间与发布人

业务要求：

- 同一流程定义下版本号唯一
- 新版本创建后初始状态为草稿
- 草稿版本允许编辑
- 已发布、已停用、已退休版本不允许直接修改核心内容
- 历史版本可复制生成新的草稿版本

### 8.3 流程版本状态管理

系统应支持流程版本生命周期管理。

建议采用以下状态：

- `DRAFT`
- `PUBLISHED`
- `INACTIVE`
- `RETIRED`

建议状态流转规则：

- `DRAFT -> PUBLISHED`
- `PUBLISHED -> INACTIVE`
- `INACTIVE -> PUBLISHED`
- `PUBLISHED -> RETIRED`
- `INACTIVE -> RETIRED`

业务要求：

1. 草稿版本发布成功后变为已发布
2. 已发布版本可被管理员停用，停用后不允许新实例发起
3. 已停用版本可重新启用
4. 已退休版本仅用于历史审计，不可恢复为可用版本
5. 已发布版本不可回退为草稿
6. 已停用版本不可回退为草稿
7. 已退休版本为终态

### 8.4 流程发布管理

系统应支持将草稿版本发布为可运行版本。

发布过程应至少包括：

- BPMN 合法性校验
- 绑定表单版本合法性校验
- 节点配置完整性校验
- 发布到 Flowable
- 保存部署结果
- 更新当前版本
- 记录发布日志

业务要求：

1. 同一流程定义任一时刻仅允许一个已发布版本
2. 发布新版本成功后，原已发布版本自动转为已停用
3. 发布失败时不得影响当前生效版本
4. 发布动作必须记录发布人、发布时间、发布结果与部署信息
5. 发布动作应具备权限控制

### 8.5 流程与表单绑定管理

系统应支持在流程版本级别绑定表单版本。

应支持的能力：

- 选择流程版本绑定的表单定义
- 选择绑定的表单版本
- 查询流程版本绑定关系
- 在实例详情中查看使用的表单版本

业务要求：

1. 一个流程版本应绑定一个主表单版本
2. 发布时绑定的表单版本必须存在且可用
3. 实例启动后，实际使用的表单版本应被锁定
4. 即使后续表单定义更新，历史实例仍保持原表单版本关联

### 8.6 节点配置管理

系统应支持对流程版本中的节点进行业务配置。

应支持的能力：

- 解析流程版本中的节点列表
- 查看节点信息
- 配置节点审批类型
- 配置审批人策略
- 配置是否允许委派、转办、退回
- 配置审批意见是否必填
- 配置 AI 建议是否启用

建议本轮支持的审批人策略包括：

- 指定用户
- 指定角色
- 指定岗位
- 发起人直属上级
- 发起人部门负责人
- 表单字段指定审批人

业务要求：

1. 节点配置必须关联到具体流程版本
2. 节点标识必须与 BPMN 中真实节点一致
3. 节点配置应随流程版本冻结
4. 已发布版本的节点配置不得直接修改
5. 节点配置本轮至少应可管理、可展示、可追溯

说明：
本轮节点配置可以先以“元数据管理”为主，不强制要求全部直接驱动运行时逻辑。运行时逐步接管可作为后续演进目标。

### 8.7 流程实例版本追溯

系统应支持从业务申请单追溯其使用的流程定义、流程版本和表单版本。

应支持的能力：

- 申请单记录流程定义 ID
- 申请单记录流程版本 ID
- 申请单记录表单版本 ID
- 申请单详情中展示流程名称、流程版本、表单版本
- 流程版本详情中展示已使用该版本的实例数量或实例列表

业务要求：

1. 每个新发起实例必须明确记录所用流程版本
2. 历史实例不得因流程升级而丢失原版本信息
3. 运维和审计人员能够基于实例反查流程版本与发布时间

### 8.8 发布日志与审计

系统应支持记录流程管理关键操作的审计日志。

应记录的关键动作包括：

- 创建流程定义
- 创建流程版本
- 发布流程版本
- 停用流程版本
- 启用流程版本
- 归档流程定义或版本

每条审计日志至少应包含：

- 操作对象
- 操作类型
- 操作结果
- 操作说明
- 操作人
- 操作时间

## 9. 流程定义与版本状态需求

### 9.1 流程定义状态

建议流程定义状态包括：

- `DRAFT`
- `ACTIVE`
- `INACTIVE`
- `ARCHIVED`

状态含义：

- `DRAFT`：已创建但尚无已发布版本
- `ACTIVE`：存在可用版本，允许发起新实例
- `INACTIVE`：流程定义暂不允许新发起
- `ARCHIVED`：流程定义归档，仅供历史查询

### 9.2 流程版本状态

建议流程版本状态包括：

- `DRAFT`
- `PUBLISHED`
- `INACTIVE`
- `RETIRED`

业务规则：

- 草稿允许编辑
- 已发布版本允许发起新实例
- 已停用版本保留历史，不允许新发起
- 已退休版本仅保留审计与复制能力

## 10. 核心业务流程

### 10.1 新建流程定义

1. 设计人员创建流程定义主档
2. 系统生成流程定义记录
3. 初始状态为 `DRAFT`

### 10.2 创建流程版本草稿

1. 设计人员在某流程定义下创建版本
2. 填写版本说明，关联 BPMN 内容和表单版本
3. 配置节点元数据
4. 版本状态为 `DRAFT`

### 10.3 发布流程版本

1. 管理员发起发布
2. 系统校验 BPMN、表单绑定、节点配置
3. 校验通过后部署到 Flowable
4. 保存部署结果
5. 新版本状态置为 `PUBLISHED`
6. 原当前版本自动转为 `INACTIVE`
7. 流程定义状态置为 `ACTIVE`
8. 写入发布日志

### 10.4 停用流程版本

1. 管理员停用当前已发布版本
2. 该版本状态置为 `INACTIVE`
3. 对应流程定义若无其他可用版本，则不可发起新实例

### 10.5 发起业务流程

1. 用户选择某流程定义发起流程
2. 系统解析其当前发布版本
3. 读取绑定的表单版本
4. 创建业务申请单与表单快照
5. 调用 Flowable 启动流程
6. 申请单记录流程定义、流程版本、表单版本信息

## 11. 数据需求

本模块建议引入以下数据对象：

- 流程定义主表
- 流程定义版本表
- 节点配置表
- 发布日志表
- 业务申请单扩展流程版本关联字段

关键数据关系包括：

- 一个流程定义对应多个流程版本
- 一个流程版本对应多个节点配置
- 一个流程版本绑定一个表单版本
- 一个业务申请单对应一个流程版本
- 一个流程版本可以被多个实例使用

## 12. 非功能需求

### 12.1 一致性要求

- 流程版本发布成功后，系统中的当前版本信息必须与 Flowable 部署结果保持一致
- 实例创建时，业务数据与版本数据必须具备事务一致性

### 12.2 可追溯性要求

- 任意流程实例都必须可追溯到具体流程版本和表单版本
- 任意发布动作都必须可追溯到操作人和操作时间

### 12.3 安全性要求

- 流程定义与版本管理接口必须做权限控制
- 发布、停用、归档操作仅允许授权角色执行

### 12.4 可维护性要求

- 流程管理层与流程执行层职责分离
- 数据模型支持后续扩展为更强的流程平台能力

### 12.5 兼容性要求

- 应兼容现有基于 Flowable 的流程执行机制
- 历史实例数据应可平滑兼容或逐步补齐版本关联信息

## 13. 约束与假设

### 13.1 约束

- 当前系统仍以 Flowable 为唯一流程执行引擎
- 当前版本以 BPMN XML 为流程定义主要载体
- 本轮不建设完整在线建模器

### 13.2 假设

- 现有动态表单版本能力可被复用
- 现有业务申请单模型允许扩展流程版本字段
- 管理端具备承载流程定义和版本页面的前端能力

## 14. 风险与待确认事项

### 14.1 风险

1. 历史数据缺少流程版本关联字段，需设计迁移或兼容策略
2. 节点配置与现有运行时逻辑之间可能存在双轨管理阶段
3. 发布失败后的状态回滚与部署一致性需重点设计

### 14.2 待确认事项

1. 发起流程时前端是按 `processKey` 选择流程，还是按 `definitionId` 选择流程
2. 节点配置本轮是否仅做管理展示，还是部分进入运行时审批人解析
3. 历史 BPMN 文件如何迁移入版本库
4. 已停用版本是否允许重新发布为当前版本
5. 流程定义归档是否需要前置条件，例如无当前发布版本

## 15. 本轮建设范围建议

建议本轮优先实现以下内容：

1. 流程定义主档管理
2. 流程版本草稿、发布、停用管理
3. BPMN 与表单版本绑定
4. 节点元数据配置管理
5. 发布审计日志
6. 实例版本追溯字段补充与查询展示

建议暂缓以下内容：

1. 完整可视化设计器
2. 任意脚本审批规则
3. 在线 BPMN 深度编辑
4. 运行中实例版本迁移

## 16. 验收标准（初版）

本模块完成后，应至少满足以下验收标准：

1. 管理员可在系统中查看全部流程定义及当前版本
2. 设计人员可创建流程版本草稿并配置基础元数据
3. 管理员可发布流程版本，并自动更新当前版本
4. 发布新版本后，旧当前版本自动转为停用
5. 系统发起流程时能够自动关联当前版本
6. 申请单详情可展示其使用的流程定义、流程版本、表单版本
7. 流程版本和发布行为具有完整审计记录
8. 历史实例不会因新版本发布而丢失原版本信息
