# 流程管理概要设计（初版）

## 1. 文档目的

本文档基于《流程管理需求分析（初版）》进一步给出流程管理模块的总体设计方案，明确模块划分、核心数据结构、关键流程、系统集成方式与兼容策略，为后续详细设计和编码实现提供依据。

本文档重点解决以下问题：

- 在现有审批系统中如何新增流程定义与版本管理能力
- 流程管理层与 Flowable 执行层如何分工
- 流程版本如何发布、停用、启用与追溯
- 发起流程时如何选择当前版本并关联到实际 Flowable 流程定义
- 如何在不破坏现有运行能力的前提下平滑引入流程管理平台层

## 2. 设计目标

本次概要设计的目标如下：

1. 在现有 Flowable 执行能力基础上补充流程管理层。
2. 建立流程定义主档、流程版本、节点配置、发布日志等核心数据对象。
3. 支持流程版本的草稿、发布、停用、退休生命周期管理。
4. 支持流程版本与表单版本绑定。
5. 支持业务实例与流程版本的强关联和可追溯。
6. 保持现有审批运行能力可用，降低对现有接口和流程执行逻辑的冲击。

## 3. 设计范围

### 3.1 本轮包含范围

- 流程定义管理
- 流程版本管理
- 流程发布管理
- 节点配置管理
- 流程版本与表单版本绑定
- 流程实例版本追溯
- 发布审计日志
- 与现有 Flowable 引擎的集成适配

### 3.2 本轮不包含范围

- 在线拖拽式 BPMN 可视化设计器
- 任意脚本引擎或 DSL 规则引擎
- 跨系统流程编排
- 流程运行中实例版本热迁移
- 多租户流程隔离
- 完整低代码平台能力

## 4. 设计原则

### 4.1 执行层与管理层分离

- Flowable 继续负责流程执行。
- 流程管理模块负责定义、版本、发布、配置、追溯。

### 4.2 已发布版本冻结

- 已发布、已停用、已退休版本不允许直接修改核心内容。
- 变更通过复制历史版本生成新草稿实现。

### 4.3 单定义单当前版本

- 同一流程定义同一时刻仅允许一个当前发布版本。

### 4.4 实例永久绑定版本

- 流程实例一旦启动，必须永久关联其使用的流程版本与表单版本。

### 4.5 渐进式演进

- 第一阶段优先实现“管理态”能力。
- 节点配置本轮以管理、展示、追溯为主，运行时逐步接管作为后续演进方向。

## 5. 总体架构设计

### 5.1 架构定位

本次设计采用“业务系统 + 流程管理层 + Flowable 引擎”三层协作模式：

1. 前端管理端
   - 提供流程定义、版本、节点配置、发布日志、实例追溯的管理页面。

2. 应用服务层
   - 提供流程管理相关 API。
   - 负责版本状态流转、发布校验、表单绑定、数据落库、实例关联。

3. Flowable 执行层
   - 负责 BPMN 部署、流程实例启动、任务流转、历史查询。

### 5.2 模块划分

建议新增以下后端模块能力：

#### 5.2.1 流程定义管理模块

职责：

- 维护流程定义主档
- 提供定义列表、详情、启停、归档能力

建议服务：

- `WorkflowDefinitionService`

#### 5.2.2 流程版本管理模块

职责：

- 创建版本草稿
- 编辑草稿
- 查询版本详情与历史版本
- 复制旧版本生成新草稿

建议服务：

- `WorkflowDefinitionVersionService`

#### 5.2.3 节点配置管理模块

职责：

- 解析 BPMN 中的节点列表
- 管理节点审批类型、审批人策略、操作能力等元数据

建议服务：

- `WorkflowNodeConfigService`

#### 5.2.4 流程发布管理模块

职责：

- 发布前校验
- 调用 Flowable 执行部署
- 更新版本状态与当前版本
- 记录发布日志

建议服务：

- `WorkflowPublishService`
- `FlowableDeploymentService`

#### 5.2.5 流程实例版本追溯模块

职责：

- 在业务实例中记录流程定义和版本信息
- 查询申请单时返回流程版本相关信息

建议服务：

- 在现有 `WorkflowService` 中增加版本写入与查询逻辑
- 或抽出 `WorkflowInstanceBindingService`

### 5.3 与现有模块的关系

本次新增模块与现有模块的关系建议如下：

- `WorkflowController / WorkflowService`
  - 继续承载流程发起、任务办理、回退、挂起等运行期能力
  - 发起流程时新增“按当前版本选版”逻辑

- `FormService`
  - 继续承载表单定义、表单版本、表单实例能力
  - 被流程版本管理和发起流程时复用

- `BizRequest / BizRequestTask / BizRequestLog`
  - 继续承载业务台账与审计
  - `BizRequest` 增加流程定义与版本关联字段

## 6. 数据模型设计

### 6.1 核心数据对象

本次设计涉及的核心数据对象如下：

1. `workflow_definition`
   - 流程定义主表

2. `workflow_definition_version`
   - 流程定义版本表

3. `workflow_node_config`
   - 节点配置表

4. `workflow_publish_log`
   - 发布日志表

5. `biz_request` 扩展字段
   - 增加流程定义和版本追溯字段

### 6.2 数据关系

核心关系如下：

- 一个流程定义对应多个流程版本
- 一个流程版本对应多个节点配置
- 一个流程版本绑定一个表单版本
- 一个流程版本可对应多个业务实例
- 一个流程定义在任一时刻最多只有一个当前发布版本

### 6.3 流程定义主表

用于描述系统中的流程主档，建议至少包含：

- 流程唯一标识 `processKey`
- 流程名称
- 分类
- 描述
- 当前状态
- 当前版本 ID
- 最新版本号
- 创建人与更新时间

### 6.4 流程版本表

用于描述某一流程定义下的具体版本，建议至少包含：

- 流程定义 ID
- 版本号
- 版本状态
- BPMN XML 内容
- BPMN 摘要
- Flowable 部署 ID
- Flowable 流程定义 ID
- 绑定表单 Key
- 绑定表单版本 ID
- 版本说明
- 发布人、发布时间

### 6.5 节点配置表

用于描述某一流程版本下各节点的业务元数据，建议至少包含：

- 流程版本 ID
- 节点 ID
- 节点名称
- 节点类型
- 审批类型
- 审批人策略
- 审批人配置 JSON
- 是否允许委派
- 是否允许转办
- 是否允许退回
- 审批意见是否必填
- AI 建议是否启用

### 6.6 实例表扩展

建议在 `biz_request` 中增加以下字段：

- `workflow_definition_id`
- `workflow_definition_version_id`
- `form_version_id`

其作用为：

- 保证任意实例可追溯到具体流程定义和版本
- 保证任意实例可追溯到具体表单版本

## 7. 状态设计

### 7.1 流程定义状态

建议流程定义状态包括：

- `DRAFT`
- `ACTIVE`
- `INACTIVE`
- `ARCHIVED`

状态说明：

- `DRAFT`：定义存在，但还没有发布版本
- `ACTIVE`：存在可用版本，允许发起新实例
- `INACTIVE`：定义存在，但暂不允许发起新实例
- `ARCHIVED`：仅保留历史查询能力

### 7.2 流程版本状态

建议流程版本状态包括：

- `DRAFT`
- `PUBLISHED`
- `INACTIVE`
- `RETIRED`

状态说明：

- `DRAFT`：草稿，可编辑
- `PUBLISHED`：当前可用版本，可发起新实例
- `INACTIVE`：停用版本，不允许新发起
- `RETIRED`：历史退休版本，仅保留审计与复制能力

### 7.3 版本状态流转

建议采用如下流转：

- `DRAFT -> PUBLISHED`
- `PUBLISHED -> INACTIVE`
- `INACTIVE -> PUBLISHED`
- `PUBLISHED -> RETIRED`
- `INACTIVE -> RETIRED`

约束如下：

1. `RETIRED` 为终态，不支持直接恢复
2. 已发布版本不可回退为草稿
3. 已停用版本不可回退为草稿
4. 已发布或已停用版本如需修改，应复制生成新的草稿版本

## 8. 关键流程设计

### 8.1 流程定义创建流程

处理步骤如下：

1. 设计人员创建流程定义主档
2. 系统校验 `processKey` 唯一性
3. 新建 `workflow_definition`
4. 初始状态置为 `DRAFT`

输出结果：

- 返回流程定义 ID
- 返回定义初始状态

### 8.2 流程版本草稿创建流程

处理步骤如下：

1. 选择某流程定义
2. 创建草稿版本
3. 生成递增版本号
4. 可从空白模板初始化，或复制上一版本 BPMN 和节点配置
5. 版本状态初始化为 `DRAFT`

设计决策：

- 本轮支持“从空白创建”和“从已有版本复制”两种方式
- 推荐默认采用“复制最近版本”降低维护成本

### 8.3 节点配置维护流程

处理步骤如下：

1. 用户打开某个草稿版本
2. 系统解析 BPMN XML 中的节点列表
3. 展示可配置节点
4. 用户配置审批方式、审批人策略、操作能力等元数据
5. 配置保存至 `workflow_node_config`

设计决策：

- 本轮节点配置主要用于管理态，不强制全量驱动运行期逻辑
- 节点配置将作为后续审批人解析器的基础输入

### 8.4 流程发布流程

流程发布是本模块的核心流程，建议按以下顺序执行：

1. 读取目标版本，确认其状态为 `DRAFT`
2. 校验流程定义存在且未归档
3. 校验 BPMN XML 非空且格式合法
4. 校验已绑定表单版本存在
5. 校验节点配置与 BPMN 节点一致性
6. 调用 Flowable 完成部署
7. 获取 `deploymentId` 与 `processDefinitionId`
8. 将目标版本状态更新为 `PUBLISHED`
9. 将该定义下原 `PUBLISHED` 版本更新为 `INACTIVE`
10. 更新 `workflow_definition.current_version_id`
11. 更新流程定义状态为 `ACTIVE`
12. 写入 `workflow_publish_log`

设计决策：

- 若部署失败，则不更新版本状态，不切换当前版本
- 发布成功后，旧当前版本自动转 `INACTIVE`
- 同一流程定义始终只有一个当前发布版本

### 8.5 流程停用流程

处理步骤如下：

1. 管理员选择当前发布版本执行停用
2. 系统校验目标版本状态为 `PUBLISHED`
3. 将该版本状态更新为 `INACTIVE`
4. 清空或重置 `workflow_definition.current_version_id`
5. 若无其他可用版本，则流程定义状态置为 `INACTIVE`
6. 写入发布日志

设计决策：

- 停用仅影响新实例发起
- 已运行实例继续按绑定版本执行

### 8.6 流程重新启用流程

处理步骤如下：

1. 管理员选择某个 `INACTIVE` 版本
2. 校验该版本具备完整部署信息或允许重新部署
3. 将当前 `PUBLISHED` 版本置为 `INACTIVE`
4. 将目标版本置为 `PUBLISHED`
5. 更新定义当前版本 ID
6. 写入发布日志

设计决策：

- 本轮默认支持“已停用版本重新启用”
- 如版本部署信息缺失，可在详细设计中选择“重新部署后启用”策略

### 8.7 发起流程选版流程

本流程用于连接流程管理层与现有流程执行层。

建议规则如下：

1. 前端仍以 `processKey` 作为默认发起标识
2. 后端根据 `processKey` 查询 `workflow_definition`
3. 读取其 `current_version_id`
4. 获取对应 `workflow_definition_version`
5. 读取该版本绑定的 `form_version_id`
6. 读取该版本记录的 `flowable_process_definition_id` 或 `processKey`
7. 创建表单实例与业务申请单
8. 调用 Flowable 启动流程实例
9. 在 `biz_request` 中写入定义 ID、版本 ID、表单版本 ID

设计决策：

- 本轮继续兼容现有按 `processKey` 发起的接口习惯
- 不要求前端直接传 `versionId`
- 当前版本选择完全由后端控制

### 8.8 实例查询与追溯流程

处理步骤如下：

1. 查询 `biz_request`
2. 根据 `workflow_definition_id` 和 `workflow_definition_version_id` 回查流程定义和版本信息
3. 根据 `form_version_id` 回查表单版本
4. 在详情页展示流程名称、版本号、表单版本号和发布时间等信息

## 9. 系统接口与分层设计

### 9.1 控制层建议

建议新增管理端控制器：

- `WorkflowDefinitionAdminController`
- `WorkflowDefinitionVersionAdminController`
- `WorkflowNodeConfigAdminController`
- `WorkflowPublishAdminController`

现有 `WorkflowController` 继续负责运行期接口。

### 9.2 服务层建议

建议服务划分如下：

- `WorkflowDefinitionService`
  - 流程定义创建、查询、启停、归档

- `WorkflowDefinitionVersionService`
  - 版本创建、复制、查询、编辑

- `WorkflowNodeConfigService`
  - 节点解析、节点配置管理

- `WorkflowPublishService`
  - 发布、停用、启用、退休

- `FlowableDeploymentService`
  - Flowable 部署封装

- `WorkflowLaunchResolverService`
  - 按 `processKey` 解析当前版本并返回可启动信息

### 9.3 仓储层建议

建议新增以下 Repository：

- `WorkflowDefinitionRepository`
- `WorkflowDefinitionVersionRepository`
- `WorkflowNodeConfigRepository`
- `WorkflowPublishLogRepository`

## 10. 与 Flowable 的集成设计

### 10.1 集成原则

- Flowable 仍是唯一执行引擎
- 流程管理模块不替代 Flowable，只补充管理能力

### 10.2 BPMN 存储策略

建议采用“双存储”策略：

1. 流程版本表存储 BPMN XML 作为平台版本事实来源
2. Flowable 部署后产生运行期流程定义记录作为执行事实来源

这样可同时满足：

- 平台级版本管理
- 执行级部署和实例运行

### 10.3 发布集成方式

发布时由 `FlowableDeploymentService` 执行：

1. 接收 BPMN XML
2. 调用 Flowable 部署 API
3. 返回 `deploymentId` 与 `processDefinitionId`
4. 交由 `WorkflowPublishService` 持久化

### 10.4 发起集成方式

发起流程时仍由现有 `WorkflowService` 承担启动流程职责，但启动前新增版本解析步骤：

1. 根据流程定义找到当前版本
2. 根据版本获取实际 Flowable 流程定义信息
3. 继续使用现有变量组装与任务记录逻辑

## 11. 节点配置策略设计

### 11.1 本轮定位

本轮节点配置主要作为“管理态元数据”，不要求 100% 驱动现有运行逻辑。

具体表现为：

- 页面上可配置
- 数据库中可持久化
- 发布前可校验
- 实例和版本可追溯

### 11.2 后续演进方向

后续可逐步扩展为运行期使用，包括：

- 发起或节点到达时自动解析审批人
- 根据节点配置决定是否允许委派、转办、回退
- 根据节点配置控制评论必填与 AI 建议启用

### 11.3 审批人策略建议

本轮建议支持以下策略枚举：

- `USER`
- `ROLE`
- `POST`
- `DEPT_MANAGER`
- `INITIATOR_SUPERVISOR`
- `FORM_FIELD`

配置以 JSON 保存，具体结构留待详细设计定义。

## 12. 权限设计

### 12.1 角色划分

- `DESIGNER`
- `ADMIN`
- `EMPLOYEE`

### 12.2 权限建议

#### DESIGNER

- 可创建流程定义
- 可创建和编辑草稿版本
- 可配置节点元数据
- 可复制历史版本
- 不默认具备发布、停用、归档权限

#### ADMIN

- 可查看全部流程定义和版本
- 可发布版本
- 可停用、启用、退休版本
- 可归档流程定义
- 可查看发布日志和实例使用情况

#### EMPLOYEE

- 仅能使用当前发布版本发起业务流程
- 可查看与自己相关实例中的流程版本信息

## 13. 兼容与迁移设计

### 13.1 现有接口兼容

本轮保持现有运行期接口兼容，尤其是：

- 继续支持按 `processKey` 发起流程
- 继续支持现有审批任务处理接口
- 继续支持现有草稿与提交接口

### 13.2 历史 BPMN 初始化

建议将当前已有 BPMN 文件初始化为流程定义与初始版本数据：

- `approvalSingle`
- `approvalCountersign`
- `approvalOrSign`
- `approvalSequential`

初始化方式建议：

1. 编写初始化脚本或启动迁移逻辑
2. 将每个已存在 BPMN 文件导入 `workflow_definition_version`
3. 标记为初始发布版本
4. 与当前 Flowable 已部署流程定义建立映射

### 13.3 历史实例兼容

历史 `biz_request` 可能缺少流程版本字段，建议采用以下策略：

1. 新增字段允许为空
2. 对历史数据执行补齐任务
3. 若无法精确补齐，则保留空值并标记为“历史未归档版本实例”

### 13.4 老数据迁移优先级

建议优先保证：

1. 新创建实例必须写入版本信息
2. 存量实例可逐步补齐，不阻塞新功能上线

## 14. 异常处理与一致性设计

### 14.1 发布异常处理

发布过程中若出现以下异常：

- BPMN 非法
- 表单版本不存在
- 节点配置缺失
- Flowable 部署失败

则处理原则为：

- 当前版本不切换
- 目标草稿版本保持 `DRAFT`
- 写入失败日志
- 返回明确错误信息

### 14.2 发起流程异常处理

若按 `processKey` 无法找到当前发布版本，则：

- 禁止发起
- 返回“当前流程无可用版本”错误

若表单版本已失效或流程版本信息不完整，则：

- 禁止发起
- 返回配置错误提示

### 14.3 一致性策略

建议：

- 数据库版本切换与业务状态更新使用事务保证一致性
- Flowable 部署属于外部系统调用，采用“先部署成功，再落库切换”的顺序减少不一致风险

## 15. 部署与实施建议

### 15.1 实施顺序

建议按以下顺序实施：

1. 新增数据表和实体
2. 实现定义、版本、节点配置、发布日志基础 CRUD
3. 实现版本状态流转和发布逻辑
4. 改造发起流程逻辑，接入当前版本选择
5. 扩展实例追溯字段与查询返回
6. 补充管理端页面

### 15.2 迭代策略

建议分两阶段推进：

#### 第一阶段

- 流程定义主档
- 流程版本管理
- 发布与停用
- 实例追溯

#### 第二阶段

- 节点配置与运行时联动
- 审批人自动解析
- 更丰富的管理端展示和分析能力

## 16. 本轮设计结论

本次概要设计采用“流程管理层附着于现有执行层”的方案，不重做流程引擎，而是在现有审批系统上补充流程定义主档、版本管理、发布管理、节点配置与实例追溯能力。

本方案的核心决策包括：

1. 继续使用 Flowable 作为唯一执行引擎
2. 新增流程定义主档和版本表作为平台级管理事实来源
3. 同一流程定义同一时刻仅允许一个 `PUBLISHED` 版本
4. 发布新版本后，旧当前版本自动转 `INACTIVE`
5. 发起流程默认按 `processKey` 查找当前版本，保持对现有接口兼容
6. 节点配置本轮以管理态元数据为主，后续逐步接入运行期解析
7. 在 `biz_request` 中补充版本追溯字段，建立实例到版本的完整链路

该方案兼顾了现有系统稳定性与后续平台化演进空间，适合作为本项目流程管理能力建设的第一阶段总体方案。
